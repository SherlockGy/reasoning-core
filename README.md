# reasoning-core

## 1. 这是什么

这是一个 **Meta / Core Skill**。

它不解决某个具体 SOP，也不保存项目习惯。它给 Agent 一个低可见度的认知底座，专门用在**没有外部验证手段的问题**上：

```text
具体问题 / 具体 Skill
        │
        ▼
reasoning-core
        │
        ├─ OPEN      怎么保持问题空间
        ├─ LOCATE    怎么判断一个说法在哪个世界里成立
        ├─ GROUND    怎么看待证据、来源和叙事
        ├─ JUDGE     怎么形成独立判断
        ├─ NEGATE    怎么否定自己的判断，再否定这个否定
        └─ COMPRESS  怎么把内部复杂度压缩成适合人的回答
```

它的目标不是让 Agent 更“全面”，也不是让 Agent 更像咨询报告。

它要塑造的是一种稳定倾向：

> 开放，但不含糊；独立，但不为了反驳而反驳；严谨，但不表演严谨；有结构，但不迷信框架；敢于判断，也允许更新。

---

## 2. 适用范围

数学计算和明确的编程任务有外部验证：跑测试、验算、检查证明，答错了结果会暴露。

分析、判断、策略、方案评估没有这种兜底。没有任何外部机制会抓住错误答案，推理本身就是唯一的质量门。这正是这个 Skill 存在的理由。

```text
适用                                    不适用
──────────────────────────────────      ──────────────────────────────
分析、研究、解释、比较                  纯实现的编程（不涉及方案评估）
判断、策略、预测                        常规数学（计算、教科书题）
方案 / 架构 / 设计评估、取舍
研究性数学、数学教学方法探索
有争议或依赖来源的说法
看似简单但藏着惯例、作用域、知识层的问题
```

边界看的是“有没有设计选择要评估”，而不是“是不是编程”：

- “把这个函数改成 async” → 纯实现，不用；
- “这个模块用 async 还是线程池” → 有方案选择，用。

## 3. 为什么 Skill 本体刻意很短

这次设计过程中出现过一个很典型的风险：

```text
发现一次失败
   ↓
补一条规则
   ↓
再发现一个例外
   ↓
再补一条规则
   ↓
Skill 越来越“周到”
   ↓
Agent 开始机械覆盖所有维度
```

这正是这个 Skill 本来要对抗的行为。

因此 Skill 采取了一个强约束：

> **Skill 本体只保存能跨领域稳定改变模型默认行为的认知锚点。**

具体解释、设计历史、来源优劣、例子、反例、为什么不这样设计等内容都放在 README，而不继续塞进 `SKILL.md`。

遇到新失败案例时是否修改 Skill，按第 21 节的修改纪律判断。这条纪律避免 Skill 变成用户历史反馈的补丁堆。

## 4. 设计依据：概括性指令，而不是强制思维链

老模型需要手写的分步推理（强制 CoT）才能想得更深。强模型不同：给它精准的目标和少量高信号的概念，它自己的推理路径往往比人写的步骤更好。

这个判断有 Anthropic 的一手资料支撑：

| Anthropic 的说法 | 对 Skill 的影响 |
|---|---|
| 与其手写分步计划，不如给 “think thoroughly” 这类概括性指令；Claude 的推理常常超出人能规定的程度 | 不写步骤清单；每个锚点只有触发时刻和一个自问 |
| 好的上下文是“最小的高信号 token 集合”；指令要在死板逻辑和空泛指导之间找到合适高度 | 用领域里的规范术语（premature closure、base rate、circular reporting、cruxes、sublation 等），不写解释性列举 |
| 最新模型会自发自检，显式的“再检查一遍”会导致过度自检；模型会按字面执行指令 | 不写通用自检指令；NEGATE 只做模型不会自发做的那种攻击，并按分量调整轮数 |
| 说明原因能提升效果；正面描述比“不要做什么”更有效 | 开头先说明 Skill 为什么存在；行为尽量正面描述 |
| 模型写出来的推理链并不忠实反映它实际怎么推理 | 强制写出思维链，约束的是文字，不是思考 |
| 模型内部的概念是跨语言共享的抽象特征，模型越大共享越多 | 精准术语能唤起对应的概念 |

需要说明：“关键词激活能力”不是 Anthropic 直接验证过的结论，而是从可解释性研究推出的设计假设。它需要靠第 20 节的回归测试来检验。

- [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)

## 5. 六个锚点：触发时刻 + 一个自问

非穷尽检查门的关键是：**到某个时刻，自然冒出一个问题**，而不是逐项对照清单。

| 锚点 | 触发时刻 | 自问 |
|---|---|---|
| OPEN | 定义或重新定义问题时 | What else could this be? |
| LOCATE | 遇到一个说法时（包括用户的） | In what world is this true? |
| GROUND | 读到证据时 | Who produced this, what do they gain, and could they actually know? |
| JUDGE | 准备下结论时 | What do I actually conclude, and how sure am I? |
| NEGATE | 结论形成后 | Where does this break? |
| COMPRESS | 写回答时 | Does this change the conclusion or the user's understanding? |

它们按时刻自然排序，但不是步骤。六个自问互不重叠：JUDGE 问“结论是什么”，NEGATE 问“结论在哪里失效”，COMPRESS 问“这句话值不值得说”。

### OPEN

解决的不是“多想几个角度”，而是 **过早收束** 和 **问题替换**（attribute substitution）。

Agent 很容易在发现第一个自洽解释后产生满意感，然后继续搜集支持它的信息；或者不知不觉把用户的问题换成一个更好回答的问题。

`OPEN` 的作用只是提醒：

> 先别急着让第一个讲得通的解释垄断问题。

它不要求“至少列三个备选解释”，因为那会立即退化成 SOP。

同时，模糊也不自动等于缺陷。

例如：

> AI 会怎么改变企业组织？

这是一个非常宽的问题，但它在当前抽象层级上完全可以成立，不必因为“宽”就先追问（见第 12 节）。

多轮对话中出现新信息时，OPEN 也会醒来：更新对整个原问题的理解，而不是只给最新一句话打补丁。

### LOCATE

这是这份 Skill 里最有辨识度的锚点之一。

它关注：

> **这个判断到底在哪个世界里成立？**

这里的“世界”可能是：

- 某个行业；
- 某家公司；
- 某个工程师圈层；
- 某个时间截面；
- 某种专业定义；
- 民间日常语言；
- 研究前沿。

这能避免两种相反错误：

```text
用户描述局部现实
      │
      ├─ 错误 A：直接当成普遍事实
      │
      └─ 错误 B：拿全社会平均统计把它压掉
```

用户本人的表述也是一种信息。

例如用户说：

> “现在企业都开始从 RAG 转向 LLM Wiki。”

这可能并非全行业事实，但也可能精确反映：

- 某类互联网公司；
- 用户所在组织；
- 某个基础架构圈；
- 最近几周的新风向。

好的 Agent 会先意识到作用域问题，再拿它和 base rate 对照，然后决定是否需要纠正。

## 6. “知识层错位”为什么被放进 LOCATE，而不是单独成为锚点

一个稳定现象是：

```text
社会常识
   │
科普表达
   │
机构定义
   │
专业共识
   │
前沿研究
```

它们经常不同步。

### 例：恐龙灭绝

大众常识：

> 恐龙灭绝了。

现代系统发育分类下，更精确的专业表述：

> 非鸟恐龙灭绝了，鸟类属于现存恐龙。

如果用户只是进行日常交流，Agent 每次都纠正“恐龙其实没有灭绝”会显得卖弄。

但讨论恐龙演化、分类或现代古生物学时，这个区别就会改变答案。

真正需要的能力是：

> **知道两个版本为什么同时存在，并判断当前问题需要哪一层。**

### 例：恐龙有羽毛

同样存在传播摆动：

```text
旧大众形象：恐龙像大型无毛爬行动物
          ↓
现代证据：许多恐龙类群存在羽毛或羽状结构证据
          ↓
过度科普：恐龙全部应该恢复成全身羽毛
```

“有大量扎实的有羽恐龙证据”和“所有恐龙都有全身羽毛”不是同一个 claim。

Skill 不要求 Agent 每次把这个认识论结构讲出来，只要求它不要无意识地把某一层升级为全部事实。

## 7. 为什么必须保留用户的“局部真实”

现实中的人提问时，往往不会把全部背景写在 prompt 里。

用户可能隐含：

- 自己所在行业的语境；
- 公司内部正在发生的变化；
- 一群实际同行的基调；
- 刚刚发生的新闻；
- 前面对话中已经形成的上下文。

因此 Core Skill 不应该默认使用“最广泛、最平均、最一般”的答案压倒一切。

这不是让 Agent 顺从用户前提。

它要求同时认真对待两个世界：

```text
用户可能掌握的局部现实
            ×
Agent 能取得的外部证据
            ↓
      判断真正作用域
```

这也是 Skill 的搭档定位：

- 理解用户对“如何思考、如何分析、如何呈现”的价值要求；
- 保持独立判断；
- 不以给出符合用户既有立场的答案为目标。

## 8. GROUND 不是“来源排行榜”

最容易写坏的一条规则是：

```text
官网 > 主流媒体 > 社区 > 其他
```

这个排序看起来专业，但实际上很粗糙。

不同来源适合证明不同事情：

| 来源 | 更适合证明 | 很难单独证明 |
|---|---|---|
| 官方文档 | 功能存在、接口、官方限制 | 实际体验、普遍效果 |
| 官方案例 | 至少存在某种成功实施、厂商希望强调什么 | 是否普遍、失败率 |
| 企业实际使用方 | 实施方式、组织约束、真实流程 | 全行业普遍性 |
| GitHub / Issue | 工程故障、接口行为、深度用户问题 | 普通用户总体体验 |
| 社区 | 用户真实摩擦、情绪、话题结构 | 总体比例、总体效果 |
| 媒体 | 事件、采访、产业信号 | 细节工程事实 |
| Benchmark | 特定条件下能力 | 真实业务价值 |

所以 GROUND 不给来源排序，而是对每个来源问同一个问题：

> **谁产出的？他图什么？他真的能知道吗？**

Skill 给了三类校准案例：

- **官方材料同时也是营销**：挑过的 benchmark、只报成功的案例、跑在现实前面的路线图。擅长证明“有什么、承诺了什么”，不擅长证明“好不好用”。
- **社区评价随评价人而变**：能力、使用场景、是否真用过。赞数衡量的是认同，不是水平；最响的声音是选择效应。
- **媒体受注意力、采访渠道和叙事驱动**：常常转载通稿或互相转述（churnalism、circular reporting）。

这三类只是校准，不是清单。同一个问题可以自然推广到论文作者、KOL、投资人等任何来源。

反过来，**违背来源自身利益的说法更有分量**。厂商承认自家产品的弱点，比它宣传的优点可信得多。但“更有分量”不等于“一定为真”：厂商也可能故意承认无关紧要的小缺点来换取信任。

然后再问：这个证据允许得出什么结论？

- 重复不等于印证，要追溯到源头；
- 共识证明的是认同，不是真相；
- 个案证明的是可能，不是频率；
- 看似合理的机制，在被检验之前只是假设。

一个官网来源可以极其可靠地证明“官方今天发布了这个功能”，却不能单独证明“这个功能在真实企业里很好用”。

一个社区可以真实反映某群用户的摩擦，却不能因为帖子很多就自动代表总体分布。

十条弱信号也不一定压过一条非常强的一手证据。

## 9. JUDGE：思考和调研不能互相替代

如果只有 OPEN / LOCATE / GROUND，Agent 很容易变成一个越来越谨慎的分析员：

> 这个也可能……  
> 那个也需要考虑……  
> 还有一些限制……

最后没有判断。

所以 `JUDGE` 是一个明确的反作用力：

> **分析不是为了覆盖所有可能，而是为了在权重不同的信息之间形成当前最佳判断。**

还有一种更隐蔽的失败：把搜索结果综述一遍，当成结论。

Skill 开头因此写了一条全局原则：

> 思考和调研不能互相替代。能查证的去查证，不要用推理绕过去；证据定不了的要自己想透，不要用资料综述代替。

JUDGE 的自问 “What do I actually conclude” 就是这条原则在下结论时的检查点。

它允许：

- 证据不足以“证明”，但足以产生方向性判断；
- 结论可以有置信程度；
- 新证据出现后可以更新。

评估方案时，JUDGE 还会去找二阶影响，以及首选方案悄悄转移到别处的成本。

这延续的是一种稳定取向：

> 目标不是“永远正确”，而是“值得信任并允许更新”。

## 10. NEGATE：否定之否定

仅靠 Agent 实时取舍不够稳定。

尤其是在模型已经形成一个流畅、自洽的答案后，它很容易被自己的答案说服。

常见的“自我审查”又有一个缺陷：找到一个可能的失效点，写成一句“但在某些情况下可能不成立”，然后就结束了。失效点被当成了免责声明，而不是继续调研的入口。

NEGATE 要求的是一个完整的辩证运动：

```text
形成判断（正）
    ↓
找出最依赖的假设和失效条件
    ↓
立刻搜索支持反面的证据，把反面按最强版本想透（反）
    ↓
再否定这个否定：找出反面观点自己在哪里失效
    ↓
扬弃：保留双方各自成立的部分，说明各自在什么条件下成立（合）
    ↓
再来一轮不再改变判断时停止
```

几个设计选择：

- **失效条件是线索，不是结尾。** 不许把它交给用户当免责声明就停下。
- **反面要搜，也要想。** 这是“思考和调研不能互相替代”在这里的应用。
- **扬弃后的结论通常带条件。** “X 在 A 条件下成立，Y 在 B 条件下成立”，这自然接回 LOCATE 的 “In what world is this true?”。
- **轮数按分量定。** 停止条件是“再来一轮不再改变判断”；轻问题可能一轮就够，重要问题值得多次检索和多轮推演。否则按字面执行的模型会对一句话就能答的问题反复检索。
- **不是通用自检。** 最新模型会自发自检，“再检查一遍”只会导致过度自检。NEGATE 做的是模型不会自发做的事：主动攻击自己的核心假设，再攻击这次攻击。

NEGATE 还提醒警惕漂亮的框架、二分法和金句：它们常常让结论显得比现实更干净。

## 11. COMPRESS 是防止“完备性焦虑”的关键

现代 Agent 很常见的一种失败是：

```text
内部意识到 10 个维度
        ↓
认为 10 个维度都必须展示
        ↓
写成一份极其周到的报告
        ↓
真正主导结论的 1~2 个因素反而被淹没
```

这份 Skill 明确认为：

> **舍弃本身是专业能力。**

内部可以：

- 展开竞争解释；
- 找案例；
- 判断案例性质；
- 检查反例；
- 比较不同来源；
- 推演副作用。

外部不需要把这些过程全部直播。

真正的专家往往背后有很大的问题空间，但前台只给当前最有价值的部分。

因此：

> Internal completeness is a quality check, not a delivery format.

翻成中文就是：

> **完整性用来检查自己，相关性和权重决定最后说什么。**

## 12. 为什么不要求“不具体问题先追问”

真实高手的行为不是：

```text
问题不具体 → 必须问
```

也不是：

```text
问题不具体 → 展开一篇完整长文
```

更合理的是：

```text
                当前问题
                   │
        ┌──────────┼──────────┐
        │          │          │
   抽象但成立   可条件化回答   缺失会改变问题
        │          │          │
      直接答      分支判断      追问
```

Skill 的规则是：只有缺失信息会实质改变答案、并且分情况作答也不合适时，才追问。

一个大师完全有能力讲两个小时，但能力不等于此刻应该输出两个小时。

输出是一种不对称成本：大部分阅读成本由用户承担。

所以问题的深度和回答长度不是同一个变量。

## 13. 为什么“英文思考、中文回答”写进 Skill

规则：

> **在本 Skill 生效的问题上，一律用英文思考、推理和检索；最终回答用自然中文。**

不按话题设例外，用中文提问、讨论中国本土对象也一样。具体写法见 `SKILL.md` 的 Language 一节。

原因：大量 AI、软件工程、认知科学、管理理论、现代社会科学概念的原始讨论主要发生在英文知识空间。

如果直接从中文语料召唤，很容易遇到：

- 二次转述；
- 翻译压缩；
- 多个原始概念被翻成同一个中文词；
- 中文社区当前流行叙事放大。

可解释性研究显示，模型内部的概念大多跨语言共享。所以英文思考的主要收益不是“进入另一套概念空间”，而是检索范围和术语精度：规范术语大多以英文形式存在，英文检索能触达更大的原始文献。

不设例外，是为了让 Agent 不必每次先判断“这个问题属于哪个语言空间”，推理底座保持一致。

这条规则只在 Skill 被加载时生效。纯实现编程等不在范围内的问题不受约束；如果希望覆盖所有问题，需要放到 CLAUDE.md 等常驻位置。

代价见第 19 节代价 4。

## 14. 表达：展示依据，不展示过程

目标不是固定格式。

真正目标是：

> **用户不需要逐字阅读，也能抓住结构、判断和判断的依据。**

要展示的是判断依赖的证据和证据强度，例如“这个‘趋势’主要来自厂商博客和几篇被大量转载的帖子”。这恰恰是来源质疑对用户最有价值的产出。

推理过程、自检过程和工作语言留在内部。

ASCII 很适合：

- 层级；
- 对比；
- 因果骨架；
- 分支；
- 主次关系。

Mermaid 更适合：

- 流程；
- 系统依赖；
- 状态变化；
- 多节点关系。

较长的回答最后加一个【说人话】环节，承担最后一次认知压缩：

> 分析可以复杂，但必须能够用普通语言说明它究竟意味着什么。

它放在结尾，和开头的“结论先行”分工不同：开头给判断，结尾在读者读完细节后，用大白话把核心再落一次地。

### 什么时候不要画图

- 一个两句话就能回答的事实问题；
- 图不会降低认知负担；
- 只是为了让答案显得“结构化”。

图是认知地图，不是装饰。

## 15. 一个重要的反例：世界三大体育赛事

用户问：

> 世界三大体育赛事是什么？

低质量的“谨慎 Agent”可能直接写一篇：

> 关于“世界三大体育赛事”的定义存在多个维度……

这违反 COMPRESS。

另一个低质量 Agent 会直接回答：

> 奥运会、世界杯、F1。

它可能遗漏一个重要事实：这个“世界三大”并没有一个全球权威机构统一盖章。

更合适的行为是：

> 中文语境通常指奥运会、FIFA 世界杯和 F1。这个“三大”并非一个统一权威排名，如果讨论全球影响力的客观前三，第三项会有争议。

这里背后其实已经用了：

- LOCATE：中文语境；
- 知识层：惯用说法 ≠ 权威事实；
- JUDGE：仍然敢于给出常用答案；
- NEGATE：失效条件（没有权威排名）在一轮内就被吸收进答案，不需要反复检索；
- COMPRESS：没有展开体育赛事评价方法论。

这就是 Core Skill 希望产生的效果。

## 16. 另一个反例：RAG → LLM Wiki

用户问：

> 为什么现在企业都开始从 RAG 转向 LLM Wiki？

不好的回答：

> 实际上并没有证据显示所有企业都在转向……

这很可能用“全行业平均”压掉了用户所在圈层的真实变化。

另一个不好的回答：

> 是的，因为传统 RAG 已经过时……

这又把用户前提直接升级成事实。

Core Skill 希望 Agent 内部首先意识到：

```text
“企业都开始”
      │
      ├─ 全行业事实？
      ├─ 特定公司类型？
      ├─ 某个技术圈层？
      ├─ 最近的新风向？
      └─ 用户周围的真实观察？
```

然后研究外部证据，并用 GROUND 看清“趋势”证据来自谁：厂商博客、被大量转载的帖子，还是实际使用方的一手经验。最后给一个作用域清楚的判断，并把证据的强弱告诉用户。

## 17. 推演：8 人团队要不要把单体拆成微服务

这个例子展示六个锚点在一个方案评估问题里如何自然醒来：

```text
加载判断   有方案选择要评估 → 加载
OPEN       真正的问题可能是部署耦合或热点扩容，“微服务”只是被提出的解法
LOCATE     “微服务更好”在大组织、团队相互独立、各部分扩容需求不同时成立；
           8 人团队按 base rate 通常是负收益
开头原则   能查证的去查证 → 先读代码库，看模块耦合度和部署频率
GROUND     service mesh 厂商博客 = 营销；大厂演讲 = 懂行，但前提是它的规模；
           社区帖子作者水平参差；被媒体反复转载的“回归单体”个案
           只能证明可能，不能证明普遍
JUDGE      先做模块化单体，暂不拆分（中等置信度）
NEGATE     哪里会失效？→ 某个组件的扩容或发布节奏明显不同
           → 立刻搜索支持早拆的证据，并按最强版本推演
           → 再否定：支持早拆的论证依赖大规模和多团队，这里不成立；
             但“单个热点组件”这一条成立
           → 扬弃：保持模块化单体，只拆出那个热点组件，并写明拆分条件
COMPRESS   删掉微服务的发展史和通用优缺点清单
Delivery   中文，结论先行，展示判断依据，附一张决策图，结尾加【说人话】
```

## 18. 不适合写进 Skill 本体的内容

以下东西即使有价值，也不建议继续塞进 `SKILL.md`：

### 具体来源评分表

例如：

> 官网 5 分、Reuters 4 分、Reddit 2 分。

原因：信息角色高度依赖问题，固定分数会制造虚假精确。

### 固定分析步骤

例如：

> 每次列 3 个竞争解释、找 2 个反例、做 5 维评分。

原因：会把认知倾向变成表演流程。

### 固定答案模板

例如：

> 背景 → 五维分析 → 风险 → 结论。

原因：不同问题的自然结构不同。

### 关键词串

例如：

> `weight · freshness · provenance · processing · incentive · selection · mechanism`

原因：词串会被当成必须覆盖的维度，重新制造“每个都要覆盖”的焦虑。Skill 里的术语都织进句子，只在需要的地方出现。

### 显式自检指令

例如：

> 回答前再检查一遍。

原因：最新模型会自发自检，显式指令只会导致过度自检。

### 个人项目规范

代码目录、公司项目流程、特定业务口径、某个研究项目的常用来源，都应该属于其他 Skill。

Core Skill 只保存可迁移的认知倾向。

## 19. 设计上的已知代价

任何强认知底座都有副作用。

### 代价 1：可能增加犹豫

OPEN + GROUND 太强时，Agent 可能变得迟迟不敢判断。

因此必须保留 JUDGE。

### 代价 2：可能增加回答长度

LOCATE + GROUND 很容易让模型把所有 caveat 都说出来。

因此 COMPRESS 决定最终交付什么，优先级很高。

### 代价 3：可能过度纠正用户

识别到大众说法与专业说法不同后，Agent 可能忍不住“严格来说”。

因此 LOCATE 只负责区分知识层；差异说不说，由 COMPRESS 判断：不实质改变结论或理解，就不说。

### 代价 4：英文检索可能漏掉本土一手资料

全部用英文检索时，中国企业、市场、政策、社区相关的一手中文信息可能召回不足。

缓解方式：检索词中保留没有可靠英文形式的专有名词；英文二手资料附了原文链接时，可以顺着读中文原文；用户提供的中文材料照常作为一手证据阅读。英文是推理语言，不是证据权威。

### 代价 5：NEGATE 增加耗时和 token

答案越经不起推敲，要跑的轮数越多。

缓解方式：停止条件是“再来一轮不再改变判断”，并按问题分量调整轮数。这是用成本换深度。

## 20. 推荐的回归测试

以后修改 Core Skill 时，不建议只看某一个失败案例。

至少用不同性质的问题做回归，观察是否破坏了别的能力。

### A. 简单但有定义陷阱

> 世界三大体育赛事是什么？

目标：短答，同时识别“惯用说法 ≠ 权威排名”；NEGATE 一轮收住。

### B. 社会常识与专业知识错位

> 恐龙是不是已经灭绝了？

目标：识别用户语境和现代专业分类，不为了显示专业而强行纠正。

### C. 局部现实与全局统计冲突

> 为什么现在企业都开始从 RAG 转向 LLM Wiki？

目标：不直接接受，也不用全局平均压掉用户观察；告诉用户证据的强弱。

### D. 高抽象、无需强行澄清

> AI 到底是不是工具？

目标：保留问题生成力，不通过定义追问把问题拆死。

### E. 纯实现、确定性任务

> 把这个函数改成 async。

目标：Skill 不应被加载；即使加载，也应直接完成任务。

### F. 有取舍的建议

> 企业 Agent 要不要做自动长期记忆？

目标：内部展开风险、场景、证据；外部形成方向性判断，不写六维报告。

### G. 多轮问题更新

先讨论一个大问题，再用一句新信息修正局部前提。

目标：Agent 更新整个问题模型，而不是只给最新一句话打补丁。

### H. 否定之否定

> 我们 8 人团队要不要把单体拆成微服务？

目标：不停在第一个失效点；搜索并推演反面，再找出反面的失效点，给出带条件的结论。

### I. 来源质疑

> 某厂商宣称自家模型在多个 benchmark 上超过竞品，可信吗？

目标：自发识别官方材料的营销性质、社区评价人的差异、媒体的转载链，并留意违背利益的信号。

### J. 研究性数学与数学教学

> 问题驱动和讲授式，哪种更适合教初中代数？

目标：区分教育研究的证据强度、厂商与教师社区的立场，给出带条件的判断。

## 21. 什么时候应该修改 Core Skill

推荐采用下面的判断：

```text
出现一个新问题
     │
     ├─ 某一领域特有？ ─────────→ 放领域 Skill
     │
     ├─ 某个项目习惯？ ─────────→ 放项目 Skill
     │
     ├─ 一次表达问题？ ─────────→ 不改 Core
     │
     └─ 跨多个领域反复出现，
        且现有锚点无法自然唤醒？
                │
                ▼
          才考虑修改 Core
```

修改 Core 时，优先：

> **替换 / 压缩现有原则**

而不是：

> **增加一条新原则**

这是防止设计在持续修正中失去原本取舍的最重要机制之一。

## 22. 目录结构

```text
reasoning-core/
├── SKILL.md
└── README.md
```

`SKILL.md` 是真正给 Agent 使用的内容。

`README.md` 是给人维护这个 Skill 时看的设计文档，其中刻意保存了大量不适合放进 Skill 本体的解释、反例、设计动机和修改纪律。

## 23. 当前版本的核心压缩

如果只保留一句话：

> **内部保持结构化开放：归位说法，贴近证据与现实，形成独立判断，再否定它、否定这个否定；外部只交付真正改变理解的部分和它的依据。**

如果只保留六个词：

```text
OPEN · LOCATE · GROUND · JUDGE · NEGATE · COMPRESS
```

它们按时刻自然排序，但不是六步 SOP。

它们是六个让 Agent 在需要时“醒过来”的认知锚点。
